| ✅ Fixed Amazon spend counting the same purchase several times | 31 Jul 2026 — Teodora reported the totals were inflated. Root cause: Amazon sends several emails per order (confirmation, dispatched, delivered, sometimes an invoice notice) and each one restates the full line items, but the unique key was `(user_id, email_id, item_name)` — a different email_id every time, so one €35 pack of nappies counted three or four times. Fixed in two layers. (1) Extraction now classifies each email (`email_kind`) and only order confirmations produce rows, so dispatch/delivery/marketing restatements never enter the table. (2) `dedupe_key` (`lib/spend-dedupe.js`) identifies the *purchase* rather than the email: order number when stated, else same-product-same-day, with the product keyed on its punctuation-stripped title. Keying on the ASIN was the obvious choice and is wrong — a test proved it: an ASIN can't be recovered from every email about an order (delivery mails often carry no product link), so "ASIN if present, else name" hands the same purchase two different keys, which is the bug itself. Price was in the key too until a parity test against the migration SQL caught JS `(3.005).toFixed(2)` = "3.00" against Postgres `round(3.005,2)` = 3.01 — same row, two keys — so it's out; it only ever separated the same product bought twice in one day. `supabase/spend-dedupe-migration.sql` cleans up existing rows: backfills the key, then a second pass merges within an order on shared ASIN or one title being a prefix of the other (a template that truncated it), collapses duplicates keeping the earliest, drops the old email-based constraint, and adds the unique index the sync now upserts against. **Verified against a real Postgres 16 instance**, not by inspection: 16 seeded rows across eight scenarios (three lifecycle emails for one order, no-order-id restatements, two separate orders of the same product, two products in one order, same ASIN with different titles, a truncated title, two size variants in one order, a second user with an identical purchase) → €346.21 collapsed to €226.84 with the variants and separate orders correctly left alone and the other user untouched; re-running changed nothing; the SQL backfill and the JS key agreed on all 11 surviving rows. **Needs `supabase/spend-dedupe-migration.sql` run in the Supabase SQL Editor** — it reports what it will merge if you run the SELECT at the bottom first. |

| ✅ Fixed mailbox connect failing for a second person — wrong-host cookie jar, found in the Vercel logs | 31 Jul 2026 — a friend tried to connect her mailbox and got a bare card reading "Error" over the hostname (screenshot, 07:49, iOS Safari). **Root cause, confirmed from Teodora's Vercel logs:** she was browsing `nona-aqmrmb280-teonona.vercel.app` — a Vercel *deployment* URL — not the custom domain. NextAuth's OAuth state/PKCE cookies are host-only (no `Domain` attribute) while the callback URL is built from `NEXTAUTH_URL` (the custom domain), so the connect started on the vercel.app host, Google/Microsoft sent the callback to the custom domain, the state cookie wasn't there, and the flow died with "State cookie was missing." — which explains the otherwise-odd detail that the error card names `www.usenona.com` even though she never typed it. Anyone handed a vercel.app link (a shared deploy URL, an old bookmark, browser autocomplete) hits this 100% of the time; it was never about her account or her mailbox. Fixed by funneling every non-canonical host to the `NEXTAUTH_URL` host in `middleware.js` when `VERCEL_ENV === "production"` — that covers the project alias and per-deployment URLs, not just the apex/www pair the first pass handled — while preview deployments keep their own hostname (OAuth can't work there regardless, since preview URLs are in neither `NEXTAUTH_URL` nor the providers' redirect allowlists). Verified locally against the exact host from her logs: it 308s to the canonical host with path and query preserved, previews and localhost pass through untouched. Also from the same logs: `/favicon.png` and `/sw.js` were being answered with a redirect to `/login` rather than the asset (neither was in the middleware allowlist) — both added. That page is identified: it's NextAuth's own built-in error page rendering its `default` case (`node_modules/next-auth/core/pages/error.js`), which is what every OAuth failure code *except* `AccessDenied`, `Verification` and `configuration` falls through to. That rules out two whole families — it was **not** Google/Microsoft refusing consent (that yields `AccessDenied` → heading "Access Denied") and **not** a missing/invalid `NEXTAUTH_SECRET`-style server misconfig (→ heading "Server error"). So the provider *did* redirect back to our own callback, which then failed: either `OAuthCallback` (state/PKCE cookie missing, or the token exchange being rejected) or `Callback` (something throwing inside the callback handler). Without the server log the two can't be separated, so the fix shipped here is to stop flying blind: (1) `pages/auth-error.js` — a real error page (`pages.error`) naming what failed in plain English per code, with next steps and the raw code kept on screen to relay; allowlisted in `middleware.js` so an expired app session mid-flow can't bounce it to `/login` and throw the code away (NextAuth warns about exactly this: "the error page should not require authentication"). (2) A NextAuth `logger` writing one greppable line per failure — `[auth] OAUTH_CALLBACK_ERROR provider=google: State cookie was missing.` — including the wrapped `cause`, never tokens or the authorization code. (3) A canonical-host redirect in `middleware.js` closing the most likely cause outright: NextAuth's state/PKCE cookies are host-only (no `Domain` attribute) while the callback URL comes from `NEXTAUTH_URL`, so anyone starting a connect on the apex domain while `NEXTAUTH_URL` points at `www` sends the callback to a host that never had the cookie — "State cookie was missing." every time. Every request now lands on the `NEXTAUTH_URL` host first; scoped strictly to that apex/www pair so `*.vercel.app` previews and localhost are untouched, and the domain is read from `NEXTAUTH_URL` rather than hardcoded. Verified locally: the error page renders the right copy per code (incl. escaping a `<script>` payload in the code param) and the redirect fires apex→www, www→apex, case-insensitively, path+query preserved, while previews/localhost/lookalike hosts pass through. **Still worth confirming on her side, now that the host bug is fixed:** Google Cloud → OAuth consent screen publishing status (README still documents the app as External + **test users**, i.e. Testing mode, where anyone not on that list is blocked outright — the friend needs adding, or the app needs publishing, before a *second* attempt can succeed); and, if the friend used Outlook, whether it's a **work/school** Microsoft account, which the `/consumers`-only provider config can't accept.
